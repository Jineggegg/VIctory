# RTX 5090 页保护与 shadow 快照偶发失败

同一地址换成新缓冲后，旧页表留下的只读记录可能让 CPU 写入悄悄漏过跟踪。这个运行时缺陷在上游就能复现。另有两项测试绕开正常提交边界，其他测试可以刷新它们的快照或清空它们的位图。两类问题均有固定顺序的复现。修复版在 RTX 5090 上默认并行全量连续 30 次通过。

## 全量对照

每个版本单独检出、使用独立 Windows target。每轮启动新的 Cargo 和 libtest 进程，不设置测试线程数。表内分母是进程运行次数，一轮多个断言失败只计一次。上游一次进程中止也计为失败。每轮的总数和完整失败用例名见[逐轮记录](logs/watch-shadow-flaky/validation.txt)。

| 版本 | 失败轮次 | 自然运行的失败用例 |
|---|---:|---|
| 上游 `63bcca4` | 10/10（100%） | 9 轮同时出现动态描述符槽和共享页表断言；其中另有两轮分别出现槽重写和视图绑定断言。其余一轮在 draw 的未对齐 UAV 用例中从描述符路径中止。 |
| 首轮优化前 `6b1e408` | 1/10（10%） | 描述符槽在准备期间被重写。 |
| 回写优化前 `dde121f` | 10/10（100%） | 10 轮都在纹理尾部读回的 RGBA8 子资源 3、第 0 行失败。 |
| 纹理修复版 `3d986b3` | 3/10（30%） | 一轮部分刷新快照，一轮同时出现 buffer retake 与首次写入前快照，一轮交错纹理读回。 |
| 本次修复 `00a3d36` | **0/30（0%）** | 每轮 303 项通过、3 项忽略。 |

此前同一纹理修复版全量失败 14/25，跳过纹理读回仍失败 1/15，单次失败率会随调度变化。本次只跑 watch、shadow 和两个 host 测试模块时，上游、首轮优化前和回写优化前各 30/30 通过。旧版本的零次自然命中不能排除缺陷。[此前验收](texture-parallel.md)

## 回写优化提交对照

为排除旧纹理读回断言，在六个提交分别用默认并行度跑 20 次 GPU 库测试，只跳过纹理读回模块。回写开发线和纹理开发线的共同祖先是 `6b1e408`；`dde121f` 是待集成的纹理对照，并非 `1dcff4d` 的直接父提交。

| 提交 | 该次改动或位置 | 所有失败轮次 | 其中 watch / shadow 失败轮次 |
|---|---|---:|---:|
| `dde121f` | 回写优化前的集成对照 | 0/20 | 0/20 |
| `1dcff4d` | 常驻工作线程池 | 2/20 | 0/20 |
| `f6f01b7` | 独立映射页分批写差异 | 1/20 | 0/20 |
| `d53a416` | 跨页 CPU 存储用例，`fb97e79` 的直接父提交 | 3/20 | 2/20 |
| `fb97e79` | 远距离刷新区间分开处理 | 2/20 | 0/20 |
| `3d986b3` | 首轮优化及纹理修复已集成 | 2/20 | 2/20 |

自然命中率没有随某个优化提交单调上升。地址跟踪给出了具体触发者：上游 `6d021fe` 的 batch 保留副本，测试在 batch 析构前释放页。后来 `f6f01b7` 的跨边界扣留、`fb97e79` 的 batch 测试和 `8da6fdc` 的同页双标记用例都增加了释放时仍有持有者的场景。跟踪直接记录到同页双标记用例释放的地址先后被 retake 或纹理用例接手。这说明测试时序扩大了旧缺陷的暴露面，现有样本不足以给某一提交估算独立的失败率增量。[逐轮对照](logs/watch-shadow-flaky/validation.txt) · [地址跟踪摘录](logs/watch-shadow-flaky/interleavings.txt)

## 运行时缺陷

1. 在真实 D3D12 设备上注册一个写监视缓冲，用绑定了共享页表的命令列表提交，等待完成。注销缓冲并释放列表和测试持有的副本。页表仍可持有旧 shadow，直到下次重建。
2. 保留地址预留，撤销该 64 KiB 页的提交并在原址以读写权限重新提交，注册新缓冲。该顺序把地址复用固定下来。新缓冲首次刷新，旧代码命中了进程内的“已保护”集合，跳过了 Windows 页保护操作。
3. CPU 写入 `0x7b`，再提交一次。旧版的主机副本得到 `0x00`。在上游和两个优化前对照上各 3/3 复现，在纹理修复版上也 3/3 复现。加入生产修复后 3/3 得到 `0x7b`。这个复现只有一个测试线程、一页数据，前一个提交已经完成。

把同址复用缩减为两次注册真实的 shadow，显式保留旧引用，即可测试更早的父子提交。完全相同的单线程用例在 `4f57f46` 连续 3 次读到 `0x7b`，在其子提交 `c75fdba` 连续 3 次读到 `0x00`。该提交让写监视内存池改用共享的页保护跟踪；父提交从 Windows 的写监视记录读取变化。由此可将这条数据丢失路径追溯到上游 `c75fdba`，可独立向上游贡献运行时修复及回归测试。[相邻提交实测](logs/watch-shadow-flaky/validation.txt)

并行全量的临时跟踪也记录到了相同的错误状态。一个回写用例释放的页还被 shadow 持有，随后被 retake 用例分配；跟踪集合认为页受保护，Windows 查询得到可写。另一轮中，新纹理的读回用例继承了两个这类页，紧接着发生行内容不符。固定旧 host batch 在释放内存后暂停，让原测试取得同一地址，retake 和部分刷新在上游各失败 3/3；纹理修复版的扫描中写入用例也失败 3/3，末尾 CPU 字节从预期的 `0xc2` 变为 `0`。这些失败无需并发运行两个 GPU 回写任务。[同页与跨测试的跟踪摘录](logs/watch-shadow-flaky/interleavings.txt) · [固定交错的逐轮结果](logs/watch-shadow-flaky/validation.txt)

新跟踪器接手地址、或运行时登记物理页别名时，在现有页保护锁内核对继承的记录。连续只读的 Windows 区域只需查询一次。若保护已经失效，撤销过期记录，标记持有者及别名，让下一次取页按实际映射重新设防。对中间撤销提交的页，打开旧守卫留下的只读片段并保留空洞。新增用例覆盖同址新缓冲、64 KiB 页中的 4 KiB 空洞和两个别名端点的保护变化。仍在使用的旧跟踪器要感知原地重映射，调用方仍须报告映射变化；此次修复覆盖新跟踪器及新登记别名接手的情形。[跟踪与别名实现](../../crates/victory-gpu/src/watch.rs)

## 测试干扰

- **部分刷新快照**。临时跟踪记录到，测试保存两页的首写前快照后，`memory::tests::a_submission_that_missed_leaves_the_copies_at_once` 的提交取走了同一 shadow 的两页。正常的提交会刷新已登记的副本，而原测试在提交锁外模拟 GPU 写入。固定插入一条实际绑定共享页表的列表，旧版得到 `[0, 102, 68, 17]`，原断言期望 `[170, 102, 0, 17]`。上游及两个优化前对照各复现 3/3。测试现使用专属的 D3D12 shadow，并保留这次干扰提交及全部原断言。
- **写入位图**。两个旧测试直接修改和清空进程共享的 GPU 位图。固定在置位后插入一个普通提交，待扣留的第二页被写回，实际为 `(170, 187)`，原断言期望 `(170, 0)`，3/3 复现。两个测试现使用已有的提交锁，从准备副本、模拟写入直到取位和断言。真实队列原本就从准备到回写持有同一把锁。[测试修改](../../crates/victory-gpu/src/shadow.rs)

新增系统调用发生在跟踪器创建和别名登记，且仅在地址有缓存守卫时触发。shadow 刷新、回写的计时循环、工作池和字节差异写入算法没有改动。若要评估性能，正式 A/B 应覆盖频繁登记或重映射物理页的场景。跟踪器或页表在提交期间创建时，这部分成本会计入端到端提交耗时。smoke 校验了字节数和内容，未作正式性能比较。
