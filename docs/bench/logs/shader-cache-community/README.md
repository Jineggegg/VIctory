# 新基线上的 shader 与 PSO 候选实验

预建键、状态恢复、跨进程库隔离和文件操作的实验均以 69e564e 为基线，在同一台 Windows 11 主机用原生 diag 构建运行，GPU 为 RTX 5090，驱动为 621.14。大档最初在 47bdb8d 上校验，正式交替 A/B 的两边统一合入 6b1e408。

## 预建键与状态覆盖

| 同一输入 | 基线 | 社区候选 | 结果 |
|---|---:|---:|---|
| 3,000 个图形键和 1,000 个计算键，每个着色器容器 64 KiB | 168.744 ms | #2787 为 23.126 ms | 中位耗时降低 86.30%，配对 95% 区间为降低 84.44% 至 86.81% |
| 单条合成记录的光栅、深度状态 | 0/2 | #3047 为 1/2，叠加 #3048 为 2/2 | #3047 恢复光栅状态，#3048 再恢复深度状态。#2787 单独运行仍为 0/2 |

键测量使用 #2787 的两条实际实现。双方共用同样的描述符和哈希，前两对预热后保留 30 对，每对交换先后顺序。95% 区间对配对样本有放回重抽 5,000 次，种子为 5090，统计量为两个中位数之比减一。应用没有提供可授权用于性能报告的游戏包，所以此结果只覆盖合成键。状态恢复对四个版本调用同一套 Pack::parse 与 Named::find，输入含非默认光栅偏移和寄存器未完整保留的深度字段。恢复的描述必须与记录里的 CityHash64 相同。[键原始值](prebuild-keys.txt) · [状态覆盖](register-coverage.txt)

## 缓存隔离与重新打开

每个方案用一个新的临时根目录，七个 Windows 原生进程依次运行硬件、同一硬件、WARP、同一 WARP、原硬件、更改翻译选项的硬件、恢复选项的原硬件。每个进程都验证实际计算 PSO 的两个 texel。建库和读库使用驱动实际创建、载入计数器。更改选项使用 shader diagnostics 的循环上限。测试 shader 不依赖该上限，所以旧命名策略也可能由驱动成功载入。对比检查配置是否独立占用磁盘空间。

| 候选 | WARP 后返回硬件 | 改变翻译选项 | 回到原选项 | 最终 PSO 文件数 |
|---|---|---|---|---:|
| 基线 | 重建 | 命中 | 命中 | 1 |
| #2646，修复 #2637 | 命中 | 命中 | 命中 | 2 |
| #2706 | 重建 | 命中 | 命中 | 1 |
| #2803，修复 #2637 | 命中 | 命中 | 命中 | 2 |
| 翻译器、选项、适配器及驱动分目录 | 命中 | 重建 | 命中 | 3 |

#2706 隔离不同的翻译器构建，本表考查的是同一构建的运行时选项。同一次测试使用同一个已安装的驱动。不同驱动号与身份不可查询的行为由单元测试覆盖。硬件与 WARP 各自另跑四个进程，依次验证首次写库、重新打开命中、注入无效 blob 后重建、再打开修复后的库。[逐进程结果](adapter-reopen.txt)

## 计算队列对图形请求的影响

使用实际的入队、出队、认领和工作线程实现，替换编译函数体以稳定控制工作时长。40 个计算任务各等待 12 ms，然后入队一个图形任务。三个版本按轮次轮换先后顺序，每个版本运行 30 个新进程。此处测量排队开销，工作函数未调用 D3D12 驱动。

| 版本 | 图形等待中位数 | 全批完成中位数 | 计算工作线程峰值 |
|---|---:|---:|---|
| 基线 | 62.309 ms | 63.231 ms | 30 次都是 8 |
| #3025 | 0.009 ms | 87.316 ms | 25 次是 7，4 次是 6，1 次是 4 |
| #3025，等待工作线程总数初始化 | 0.031 ms | 75.622 ms | 30 次都是 7 |

#3025 的一部分线程启动时可能读到默认线程数 1。等待 OnceLock 完成初始化能稳定保留 7 个计算工作线程。两种优先方案都缩短了图形排队，同时延长了纯计算为主的整批用时。16 次同步 PSO 预建不经过该队列，无法代替这项测试。[调度原始值](pso-queue.txt)

## 字节一致性和 Windows 测试

分页正确性修复改变了预期 DXIL。在修复前，改前与候选的 20 个 shader 都是 77,333 字节，集合 BLAKE3 为 `6a3b8c756f04aa62ade1d92871430c8a1326354061bb5d52a9266ddb2936090f`。在 69e564e 基线上，de496c3 的三个独立 Windows smoke 进程均输出 88,177 字节，集合 BLAKE3 为 `a0c629eda000e64f6a98240935c1cda672a72df20184c884832d2da2831b69f8`，与同版基线一致。测试在每个进程内逐字节核对了无缓存、冷写和命中三条路径。

集成实验 be6990d 的五个受影响包在 Windows 原生 diag 构建中通过 633 项测试，9 项按源代码标记忽略。这个构建同时包含预建键复用、寄存器状态恢复、独立持久化 early list，以及把资源元数据放进受同一校验和保护的 shader 条目。使用上游 #2828 文件共享方式构造的并发用例也在项目分支上单独通过。[测试计数](native-test-summary.txt)

## 冷写文件分项和大档校验

在 Windows 原生进程中，两版各记录了 600 次条目发布。基线每批 20 个 shader 在分片目录上花费的中位数为 2.768 ms，临时文件创建为 1.854 ms，写内容为 0.867 ms，重命名发布为 3.374 ms。平铺格式将逐条目录操作移到批次之外，但每批的重命名仍需 3.568 ms。详见逐条和逐批的中位数、p95、p99。[文件操作统计](cache-file-operations.md) · [原始计时](cache-file-operations.txt)

## 大库重新打开

分层实验先写 32 个普通条目，然后把后续条目放入带校验和的 SQLite WAL 表。32 是本实验选定的切换点，覆盖原来的 20 个 shader 场景。数据库写入失败时仍可发布原子替换的单条目文件。de679c6 在 Windows 原生通过 11 项缓存测试，包含另一进程已打开缓存时出现数据库、并发发布相同键、未完成事务强制退出、行损坏后重新翻译、整库损坏后从普通文件命中。

为检查跨进程启动开销，专用场景在一个进程写入完整的 2,000 个 shader，随后启动三个新进程，分别读取最先写入的 20 个、中间的 20 个和全部条目。计时包括配置缓存和读取所选条目。期望值由写入进程在计时后计算，逐条保存 DXIL 散列。后续每个进程均检查命中状态和这些散列。每个子进程在读取期望散列前记录 Windows 工作集峰值和专用提交内存峰值，单位为字节。[场景定义](large-disk-reopen.json)
