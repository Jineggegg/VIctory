# RTX 5090 标记页回写与副本刷新

测试使用 Windows 11、GeForce RTX 5090 32 GB、621.14 驱动、Core Ultra 9 285K 和 128 GB DDR5。256 MiB 场景处理 4096 个 64 KiB 页。刷新先复制并逐页检查全部 256 MiB。回写经过 Host::execute 对重复声明和 withheld 范围的处理，再检查 240 MiB 新内容和 16 MiB 保留内容。旧报告的 90.78 ms 与 42.27 ms 来自另一轮运行；本报告的改变量都取自同窗口交替样本。[测量方法](method.md)

## 社区方案初筛

初筛使用同一份开发基线和同一测试入口。17 个候选各测三档，每档 15 对。加上 #2428 的稀疏场景，共 52 组、780 对；另有 5 对用于核对中场前后的漂移。各候选的 256 MiB 中位数、逐项区间、正确性和取舍列在同一张表中。三档明细另列 p95、p99 及校正后的中位数变化区间。[逐候选对照表](screen-medium.md) · [三档完整数据](screen.json) · [各二进制与校验量](candidate-workloads.json)

在同一份 256 MiB 副本两端各提交 1 MiB 视图，然后再申请中间 64 KiB 页。原版第一次复制 256 MiB，中间页已经是最新内容，第二次复制 0 字节。#2428 第一次只复制 2 MiB，第二次再复制 64 KiB。两次总刷新中位数从 33.4113 ms 降到 0.3270 ms，配对变化 −99.02%（95% 区间 −99.03% 至 −99.00%）。单独看第二次，耗时从 0.7 µs 增到 16.3 µs。三处视图的全部内容都通过检查。[稀疏场景配对结果](screen/sparse2428/paired.json)

#3069 通过 HLE 映射写回物理页，在标准场景对 3840 个有效页尝试了 3840 次，命中 0 次；实际 HLE 物理页别名映射用例通过。#3118 在相同场景封住了 3840 个新页，但本次提交结束前仍兑现回写。封住的页能由普通 CPU 指令触发，内核读入接口的行为则不同。以上两项都单独保留路径命中的输出。[#3069 热点路径](preflight/3069-real-path.txt) · [HLE 正例](preflight/3069-hle.txt) · [#3118 热点路径](preflight/3118-real-path.txt) · [CPU 指令读取正例](preflight/3118-cpu-read.txt)

#2918 原版把实际差异字节数计入诊断值。该版本在 256 MiB 时报告 250,656,000 字节，逐页核查得到 0 个错误字节，所以另测了一版只统一诊断计数的实现。#1998 原版报告 266,338,304 字节，直接读标题内存发现应保留的 224 页中有 14,621,600 个字节错误。两种情况都保留了原始失败输出。[诊断计数](preflight/rejected-counts.json) · [独立内容核查](preflight/title-bytes.json)

## 并发与范围正确性

GPU 只应回写与执行前快照不同的字节。在 CPU 读取后、GPU 回写前安排一次真实的 CPU 写入，上游和开发基线都曾把该字节覆回 0。另一次重叠声明还可能把 CPU 的最新值恢复为已经过期的值。独立修复只写连续的 GPU 差异并更新已合并的局部快照。原用例在 RTX 5090 和 WARP 上均由失败变为通过。以纯上游为起点的独立提交是 b1fb182，开发基线上的等价提交是 28de15a。[硬件、WARP、上游 PR 逐项对照](snapshot/README.md)

标记回写在页受保护时取比较依据，将变更压成每 16 字节一份的位掩码。全变块可以一次存储；有 CPU 保留字节的块只存掩码指示的字节。实际写完并重新保护后再从标题内存刷新副本。只有属于同一私有写跟踪分配的大批独立页才分给多个工作者。可能映射同一物理页的视图保序，普通回写完成后才让 withheld 别名失效。位图末字保留实际页的 31 个位置，只有最后一个溢出位被丢弃。定点检查包括一条跨 64 KiB 边界的 CPU 写指令，以及重叠快照不得重放 CPU 字节。[五项定点检查](candidate-correctness.json)

两个提交列表可以在同一页分别声明有效写入和 withheld 写入。移植 #1986 的区间处理后，有效范围的四个字节回写为 5A，保留范围在标题内存中仍为 00，同时在 GPU 副本中保有 A5。仅按整页判断的基线会把四个有效字节全部丢掉。[同页声明实测](withheld/matrix.json)

早期还试过顺序写精确区间、每个任务只处理一页、四个工作者每块四页，以及再压缩稀疏掩码。这些烟测没有正式空闲控制，只用于选择后续实验。正式候选保留了每块最多八页和紧凑掩码，并单独比较两种实际存储与刷新实现。XCL 方向按公开思路独立实现分块调度，没有带入 GPL-2.0-only 源码。[试验记录](informal-experiments.json)

## 中档终选与内存

完整 19 项套件每臂运行 30 次。256 MiB 标记页回写的中位数为基线 80.06 ms、本地方案 38.28 ms、社区组合 38.66 ms。对应副本刷新的中位数为 35.54、19.99、21.60 ms。本地对社区组合的回写配对区间跨零，刷新另快 7.81%（95% 区间 6.11% 至 9.75%）。其余 17 项耗时中，本地方案没有任何一项在逐项 95% 区间内显示中位数增加。原版中档 gradient 的完整纹理更新另显示 +1.87%（逐项 +0.72% 至 +3.41%，多项校正 −3.86% 至 +5.85%）；完整 19 项套件未重复出这个差异。所有尾分位都列在表里。[本地对基线，19 项及内存](full19-B1-vs-A.md) · [社区组合对基线](full19-B2-vs-A.md) · [本地对社区组合](full19-B1-vs-B2.md)

三个版本采样到的本地显存峰值中位数均为 232.542 MB。进程工作集峰值中位数从 1117.010 MiB 增至本地方案的 1118.348 MiB、社区组合的 1118.420 MiB。本地方案增加 1.338 MiB，配对变化 +0.120%（逐项 95% 区间 +0.096% 至 +0.758%），增量可测。区间较宽，因此也提供逐轮数据。[正式原始结果](final/all19/) · [Windows 线程栈观测](memory/stacks.md)

同一组二进制又在普通构建间隙运行六轮。回写之后，基线、本地方案和社区组合的原生线程数中位数分别为 25、32、35，所有线程实际驻留的栈合计分别为 472、588、610 KiB。相对基线的 116 和 138 KiB 只解释了部分工作集差额。按代码，每个八页回写分块最多暂存 64 KiB 的字节变化掩码，再复用 8 KiB 的标题读取区，最多八个分块同时执行。Windows 池按需提交工作，第一次遇到大范围刷新时才观察到七个额外工作线程。直接缩小线程保留栈不能消除全部峰值差额。[进程级观测方法与各阶段值](memory/stacks.md)

原仓库 compare-hot.py 的独立样本对照也保留。所用版本为 69e564e，此后工具迁移为 hot.sh/xtask。终选选择依据是同一轮内的三组配对。[本地对基线](compare-hot-B1-vs-A.md) · [社区组合对基线](compare-hot-B2-vs-A.md)

完整 19 项中的 1,300 描述符同步有一个尾部读数需要保留。中位数从 0.936 到 0.946 ms（配对 +1.38%，95% 区间 −0.84% 至 +5.14%），p95 从 1.019 到 1.096 ms（+7.52%，+1.90% 至 +12.61%），p99 从 1.021 到 1.105 ms（+8.14%，+2.63% 至 +10.86%）。按 19 项分别对 p95、p99 作多项校正后，两条区间均跨零。这项在每个新进程中都先于该次大副本回写运行。30 次的 p99 是单个最大值，现有样本不能把差异归因于回写，也不能据此保证尾部完全持平。

另在合并纹理优化后的最终代码上检查内存与负载的关系。16 MiB、256 MiB 和 1 GiB 每档独立跑 6 对同入口进程，配对峰值差的中位数依次为 +0.91、+1.06、+0.65 MiB。负载扩大 64 倍时未观察到额外内存按负载成比例增长。另一个进程连续跑 3000 轮，每轮均包括刷新、标记回写和真实 CPU 并发写。最后 550 轮中工作集和私有提交各自只波动 64 KiB，句柄数和线程数保持固定。[三档对照及区间](memory/scale.md) · [1000 轮与 3000 轮核验](memory/lifetime.md)
