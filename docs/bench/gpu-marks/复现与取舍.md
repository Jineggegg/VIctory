# 测试条件与取舍

## 数据怎么读

历史两项使用 2f0d7ea 和 69e564e 的原始场景。其后比较采用带相同扩充测试的分支，测每次启动后的新派发。因此两个系列各读各的 A/B；不能用跨系列的绝对耗时计算加速比。所有采样由 Windows 原生程序执行，使用同机 RTX 5090、驱动 621.14、交替 AB/BA、提前预热 3 秒、P0/P1、核心至少 2500 MHz、显存至少 13000 MHz、PCIe Gen5 x16。11 项的综合结论按同组同时 95% 区间判断。循环八次的单项和同时区间支持不同强度的结论。

历史对照来自[主线程的 30 对配对统计](../logs/gpu-marks/historical/paired.json)。新增的八轮 A/B 共 114 对，所有输出校验通过，门槛无效样本为零。[实测报告](GPU页标记与地址解析实测.md)按轮链接到两端样本、配对统计、运行日志和遥测。12 对和 30 对的 p99 都取本轮最大值。11 项场景的清单在 [GPU 场景清单](../../../tools/bench/suites/gpu-page-marks.json)。

合并分支保留页粒度、循环条件与上限。循环内逐次数据依赖仍然存在。页表、描述符延迟和循环退出在普通游戏 draw 上各占多少，本轮没有独立硬件计数可量化。社区的整帧成绩不能转用为本机游戏帧时间。

跨页行为沿用 e815cef 的末字节查表。社区的控制实验和 4 KiB 讨论是选择实验的背景。此分支沿用现有标记粒度，测出的是减少重复访问的收益；4 KiB 额外原子操作的代价本轮没有重测。[控制实验 #2695](https://github.com/Marvisak/VIctory/issues/2695) · [粒度讨论 #2409](https://github.com/Marvisak/VIctory/pull/2409)

[问题 #3028](https://github.com/Marvisak/VIctory/issues/3028) 的普通 draw 与本轮 dispatch 工作负载不同；没有用该 issue 的时间填充本机结果。位图迁移的集成讨论见 [#2175](https://github.com/Marvisak/VIctory/pull/2175) 和 [#2465](https://github.com/Marvisak/VIctory/pull/2465)。

## 工作负载与边界

- 计算场景使用 4096 × 64 个线程。相同输入生成同页、两页、16 页以及双字跨页的访问，双字写起始偏移依次为 4、12、20 字节，每个 64 KiB 边界有一笔写横跨两页。按 CPU 计算的输出校验线程结果。标题写只激活奇数 lane，共享页与散页分别测量。
- 标准循环每 lane 串行依赖 8 次全局 32 位读取。变长循环按组在 1 到 64 次之间提前退出，校验返回值。两种场景都执行真实的访存和循环指令。
- 三个像素场景使用窄覆盖和横向 quad 数据读取形成实际 helper lane。分别测视图同页写、视图散页写、纯描述符分页读。逐位核对读写位图，同时检查有覆盖与无覆盖位置的结果。
- 单元测试逐位验证不同 EXEC 掩码、已置位、跨 256 MiB 和 4 GiB 边界、重定向到空缓冲的原虚拟页 4296、第一个组提前返回和不同设备能力的缓存命中。标题内存的像素写保留每个活动 lane 的更新；视图像素标记只让实际覆盖的 lane 代表相同页。波宽测试在 NVIDIA RTX 5090（32）、Intel Graphics（报告 8–32）和 WARP（报告 4）上核对标题位图。固定 Wave64 仅在设备支持时启用；本机没有 AMD Wave64 或旧代 NVIDIA 的实测成绩。
- 缺少 WaveOps 的设备走标量路径。两种能力生成相异的缓存项和带标记的 DXIL；相同能力复用缓存；管线库名含最终 DXIL，同一无标记全屏顶点 shader 在两种能力下字节相同。emit/shader.rs 未修改。

AMD Wave32/Wave64 使用设备实际的活动 lane 集与 wave 按位或。写位图每个字 32 位，wave 宽度可以为 64；若横跨不同的位图字，算法保留每个 lane 自己的字与位。Intel 的标题写正确性已实测；其性能和旧代 NVIDIA 的性能需各自硬件计时。分页只在要求它的设备和访问上生效，关掉分页时没有虚拟页标记可复用。

## DXIL 与 PIX

下表列出 DXC 反汇编中的静态调用点。同一调用点在循环内、每个 lane 或每条非活动分支的实际执行次数不同。

| 版本 | 同页视图 rawBufferLoad / atomicBinOp / heap handle / wave 调用 | 8 次循环 rawBufferLoad / atomicBinOp / heap handle / wave 调用 |
|---|---:|---:|
| 分页前 | 4 / 2 / 1 / 0 | 9 / 3 / 2 / 0 |
| 分页后 | 6 / 3 / 1 / 0 | 13 / 5 / 2 / 0 |
| #2167 | 5 / 3 / 1 / 0 | 12 / 5 / 2 / 0 |
| #2755 | 6 / 3 / 1 / 0 | 14 / 5 / 2 / 3 |
| #2958 | 6 / 3 / 1 / 6 | 13 / 5 / 2 / 8 |
| 两个 wave 改动加成对读取 | 5 / 3 / 1 / 6 | 12 / 5 / 2 / 11 |
| 再复用入口读标记 | 5 / 3 / 1 / 6 | 11 / 4 / 2 / 9 |
| 最终转译 | 4 / 3 / 1 / 4 | 10 / 4 / 2 / 7 |

最终两项的固定页入口各有 3 个 threadId 调用，用于选择派发原点。标准循环保留两个 heap handle 静态构造点。最终标准循环体仍依次读取一级条目、二级相邻字段、描述符虚拟页表，再按 heap handle 读取 guest 数据；DXIL 中循环上限检查仍为 1,048,576。合并后仍有依赖的页表读取和资源访问；不能由静态调用数推算驱动生成的 SASS 周期。

像素样例也反映了选主成本。分页像素场景的 rawBufferLoad / atomicBinOp 从 6 / 3 变为 5 / 3，最终有 3 处 isHelperLane 调用；无分页共享视图从 4 / 2 变为 3 / 2，有 2 处 isHelperLane。奇数 lane 标题写则从 6 / 2 变为 7 / 2，新增先查位和 wave 操作，因此单看静态指令数会漏掉运行时跳过的访问。

PIX 从分页后原树和两项社区 wave 合并版导出两组 PSO，以及各自的两个 Dispatch(4096,1,1)。两个 dispatch 前后均有 GPU 时间戳。用 Windows XPRESS 解压 PIX 的 resources.bin，并用 DXC 反汇编实际绑定的 4 个 PSO shader。原树两个都与独立导出的 DXIL 逐字节相同。

| PIX 捕获 | 着色器 | DXIL 字节 | rawBufferLoad | atomicBinOp | wave 调用 |
|---|---|---:|---:|---:|---:|
| extended-reference | wave_page_marks | 3176 | 6 | 3 | 0 |
| extended-reference | loop_page_lookup | 3968 | 13 | 5 | 0 |
| two-waves | wave_page_marks | 3416 | 6 | 3 | 6 |
| two-waves | loop_page_lookup | 4476 | 14 | 5 | 11 |

PIX 事件计数回放返回 E_PIX_FEATURE_REQUIRES_DEVELOPER_MODE；Nsight Graphics 已连接目标，驱动未开放 GPU Performance Counters。此环境没有厂商指令吞吐、缓存未命中或 SM stall 的测量。
